# 证据规则与角色层级硬约束规范（Evidence Rules）

简历优化的上限取决于真实度与防伪边界。任何脱离客观证据的高势能措辞，在严格的尽职调查（Due Diligence）、背景调查（Background Check）及白板技术深挖面前都会演变为灾难性风险。

本规范确立了 OfferGet 体系的核心准则：**角色 0-3 级硬约束、最小闭环 (Scope) 判定标准、A/B/C/D 证据源层级体系、5 档核验状态，以及自动化静态审计规则**。

## 一、角色强度 0-3 级硬约束标准

在描述任何工作经历或项目贡献时，角色词必须受到严密的事实约束。依据输入事实证据，分为以下 4 个角色等级：

```text
[Level 0: 规划/探索/预研] ──(强时态约束，严禁完成态动词)──> 标明「当前方向/规划中」
[Level 1: 参与/协助/共建] ──(边界锁定，严禁全局Owner)────> 标明「系统级共建者/核心参与者」
[Level 2: 主导/主要负责] ──(分工明确，指出策略边界)────> 标明「策略架构Owner/方向负责人」
[Level 3: 独立负责/从0到1] ─(必须锚定最小闭环Scope)────> 标明「模块级Owner / 从0→1打通X链路」
```

### 1.1 Level 0: 规划 / 探索 / 预研 (Planned / Exploratory)
- **事实定义**：该项目尚处于方案调研、概念验证（PoC）、代码起步或季度规划阶段，尚未全量上线产生确定性业务/线上产物。
- **时态硬约束**：
  - **严禁使用的完成态动词**：`已上线`、`已达成`、`完成`、`实现`、`主导`、`Owner`、`核心作者`、`突破`、`提升约 X%`、`降低约 Y%`；
  - **合规表述**：必须显式标注 `当前方向`、`规划中`、`技术预研`、`正在探索`。
- **正反范例**：
  - ❌ **严重违规**：
    > “主导长程代码智能体自动修复系统上线，在生产环境将 Bug 修复率提升 30%。”（实际只是刚跑通本地 Demo）
  - ✅ **合规高势能**：
    > “**当前规划与探索方向**：面向多智能体长程上下文一致性，预研基于快照持久化的回滚机制与微压缩沙箱。”

---

### 1.2 Level 1: 参与 / 协助 / 共建 (Contributor / Participant)
- **事实定义**：作为团队成员之一，负责特定的子模块、编写部分逻辑代码、协助核心排错或提交过部分 PR。
- **边界硬约束**：
  - **严禁跨层级升格**：严禁写为“全局系统 Owner”、“架构主导者”或“核心作者”；
  - **允许的升维表述**：可使用 `系统级共建者`、`核心参与者`、`模块贡献者`；
  - **必须限定子模块**：写清自己贡献的具体功能块（如前端展现、特定数据管道清洗、某几个 API 端点）。
- **正反范例**：
  - ❌ **严重违规**：
    > “开源分布式向量数据库核心作者与架构负责人。”（实际仅提过 3 个文档与修复 typo 的 PR）
  - ✅ **合规高势能**：
    > “**开源分布式向量数据库活跃共建者**：主要贡献 Python SDK 异步客户端封装与连接池重试容错机制，累计向社区提交并合并 8 个核心 PR。”

---

### 1.3 Level 2: 主导 / 主要负责 (Lead / Maintainer)
- **事实定义**：负责一个明确的技术方向、算法策略或子系统的主体设计，承担核心 Code Review、技术选型与关键故障攻坚，但系统可能依赖更宏观的平台基础设施或其他团队底座。
- **边界硬约束**：
  - **职责切分声明**：必须将团队平台与个人负责的算法/架构策略区分开；
  - **推荐表述**：`策略架构 Owner`、`算法链路负责人`、`开源项目 Maintainer`。
- **正反范例**：
  - ❌ **模糊掠美**：
    > “从 0 到 1 打造了支撑全公司千万日活的 AI 推荐大模型中台。”（实际中台由数十人团队共同维护）
  - ✅ **精准高势能**：
    > “**推荐大模型召回策略架构 Owner**：负责多模态特征融合与负采样重构，打通离线特征抽取至在线双塔召回链路，支撑业务千万级日活请求。”

---

### 1.4 Level 3: 独立负责 / 从 0 到 1 (Independent Owner)
- **事实定义**：在明确限定的业务或技术闭环内，独立完成从需求抽象、技术选型、架构设计、核心编码、评测调优至最终上线部署的全流程。
- **边界硬约束**：
  - **必须限定最小可证明闭环 (Scope)**：禁止无界限的“从 0 到 1”，必须写清这个“0 到 1”发生在哪一个具体工程边界内；
  - **具备端到端交付物**：必须能拿出可运行的独立模块、CLI 终端命令、代码仓库、已上线服务或独立评测报告。
- **正反范例**：
  - ❌ **失控无界**：
    > “项目 Owner，从 0 到 1 负责公司所有大模型训练与推理。”
  - ✅ **闭环受控**：
    > “**NL2SQL ModelOps 全链路 Owner**：从 0 到 1 打通 Executable SQL Cleaning -> Short COT -> GRPO 强化学习 -> AWQ 量化 -> SGLang Serving 的完整技术闭环。”

## 二、最小可证明闭环 (Minimal Proving Scope) 原则

在撰写“Owner”和“从 0 到 1”时，**必须执行“Owner 化拆分”**。寻找候选人真正拥有完全决策权与实现权的最小单元：

| 原始模糊边界 (易被质疑) | 拆分后的最小可证明闭环 (无可辩驳) | 闭环覆盖的端到端技术链路 (Proof Chain) |
|:---|:---|:---|
| “负责公司大模型系统” | **离线评测与数据蒸馏流水线 Owner** | `样本配比 -> 规则过滤 -> LLM-as-Judge 打分 -> 错题沉淀` |
| “负责推荐算法” | **多模态冷启动特征召回链路 Owner** | `OCR/ASR抽取 -> LanguageBind 对齐 -> 离线落盘 -> 准实时召回` |
| “负责开源智能体项目” | **动态插件协议与执行沙箱模块 Owner** | `MCP 协议适配 -> Docker 容器隔离 -> 退出码捕获 -> 状态回滚` |
| “负责后端高并发架构” | **订单幂等扣减与异步对账引擎 Owner** | `Redis 分布式锁 -> 内存环形队列 -> MySQL Binlog 解析 -> 异常对账` |

> **法则**：宁可把 Scope 缩窄到一个具体链路当 100% 的 Owner，也绝不要把全局平台写在自己名下当 10% 的参与者。

## 三、A/B/C/D 证据来源层级分类

为每一项简历陈述建立来源定级，在背景调查与审计中优先使用最高层级证据：

| 层级 | 证据源属性 | 典型证据示例 | 能够证明的核心事实 | 证明效力与法律/背调权重 |
|:---:|:---|:---|:---|:---|
| **Level A** | **官方且同期的直接第一方记录** | 学历学位证书、学信网报告、带公章离职证明、HR/背调系统核验、官方项目正式任命书、已合并 Git Commit/PR、国家发明专利授权书、顶级学术会议第一作者出版记录。 | 正式法定角色、教育背景、真实任职时间戳、可证明的代码资产所有权、排他性奖项。 | **绝对最高（不可辩驳）** |
| **Level B** | **可复现的公开一手记录** | GitHub/GitLab 仓库主分支公开 Commit 记录、Release Notes、第一方官方技术博客署名、个人技术讲演录像、官方 Wayback Machine 历史快照、线上生产服务公开 API 文档。 | 实际公开交付物、功能代码所有权、代码提交时间跨度、技术演讲与技术方案主张。 | **极高（公众可随时复现验证）** |
| **Level C** | **有署名的第三方/二手报道** | 知名科技媒体专题报道（带链接）、第三方研究机构分析报告、业界权威评测排行榜公开截图与链接、具有实名签名的推荐信。 | 行业影响力、间接声誉、商业化成果上下文背景。 | **中等（需排除软文或公关宣传偏差）** |
| **Level D** | **未核验的私有陈述与弱证据** | 候选人口头陈述、匿名社区帖子、无上下文/无时间戳的代码截图、未经认证的私有聊天记录、自制展示 PPT。 | 仅能证明“当事人曾做此声称”，无法独立证明事实真伪。 | **低（在审计报告中必须标注未核验）** |

## 四、5 档核验状态判定规则

对简历中的每一条关键主张（特别是 Title、角色、指标、开源贡献），经过证据链交叉比对后，判定为以下 5 种状态之一：

### 4.1 `corroborated` (已证实)
- **判定标准**：存在独立的 **Level A 或 Level B 级直接证据**，能够完全覆盖简历中主张的关键措辞、角色等级、所属机构与成果范围。
- **示例**：声称“Apache 某项目 Committer”，在 Apache 官方网站项目 Roster 名单中可精确检索到个人 ID 与邮箱。

### 4.2 `partially_corroborated` (部分证实)
- **判定标准**：事实锚点确实存在，但简历中**人为扩大了其边界、角色等级或成果作用域**。
- **示例**：声称“主导 1.0 到 2.0 整体架构重写”，但公开仓库 Commit 记录显示候选人主要贡献集中在文档优化、测试用例编写与少量 Bug 修复，核心核心调度引擎由他人提交。

### 4.3 `contradicted` (存在直接矛盾)
- **判定标准**：简历陈述与已确凿的客观事实或权威时间戳发生**不可调和的逻辑或物理冲突**。
- **常见类型**：
  1. **同屏数学矛盾**：给出的分子、分母计算得出的百分比与展示百分比明显不符；
  2. **学籍学位冲突**：声称某常春藤高校全日制硕士，官方学籍记录显示为短期非全日制培训结业证书；
  3. **时间重叠冲突**：在同一时间段内，声称在两家全职公司同时担任全职团队负责人。

### 4.4 `unsupported` (缺乏支持)
- **判定标准**：对可公开检索的范围穷尽调查后，**未能找到任何能够证明该主张的外部有效证据**。常发生于“全球首个”、“全网第一”、“最年轻”等排他性最高级陈述。
- **规则**：报告必须注明检索边界与关键词，并提示候选人补充第一方证据。

### 4.5 `unverifiable` (暂不可核验)
- **判定标准**：该主张属于涉及企业商业机密、私有未公开系统、内部未脱敏数据或内部口头表彰，**在客观上仅能通过原雇主私有档案才能核查**。
- **规则**：没有公开证据不等于造假，应标注其为暂不可核验，提醒面试官在现场通过白板推演进行实操核查。

## 五、置信度分级与反证检查清单

### 5.1 置信度分级 (Confidence Levels)
- `high`：由 Level A 直接凭证或确定性数学重算驱动，结论不可推翻；
- `medium`：多个独立第三方证据指向同一结论，但仍可能存在未知的内部例外；
- `low`：主要基于推断或证据链存在缺失。

### 5.2 反证检查清单 (Counter-Evidence Checklist)
在给出一项不利判定（如判定候选人夸大或矛盾）前，审计员必须执行以下 5 项防御性反证检查：
1. **是否存在被 Squash 或镜像的历史 Commit？**（内部 Git 可能通过服务账号或统一机器人向主干合并）；
2. **官方名册是否为全量名册？**（有些官网展示的是当前主要负责人名单，而非历史完整贡献者全集）；
3. **争议词汇是否存在合理的宽泛定义？**（例如海外对“Research Intern”与国内对“实习算法工程师”的语意边界差异）；
4. **是否存在合理的计算口径重叠？**（例如相对提升 vs 百分点绝对提升，候选人是否由于表述不规范而非恶意捏造）；
5. **候选人是否通过其他非公开渠道达成了成果？**（如向客户交付了私有化部署版本）。

## 六、审计引擎静态拦截规则对照

在 `core/resume_auditor.py` 中，静态检查器执行以下无条件拦截：

```python
# 1. 角色升维拦截 (Role Elevation Gate)
if claimed_rank > ground_truth_level:
    trigger_critical_finding("Role elevation detected")

# 2. Level 0 规划时态违规拦截 (Planning Tense Check)
if claimed_rank == 0 or status == "planned":
    for forbidden in ["已上线", "实现", "主导", "突破", "降低约"]:
        if forbidden in text:
            trigger_critical_finding("Planning tense violation")

# 3. Level 3 独立负责无 Scope 拦截 (Unbounded Scope Check)
if claimed_rank == 3 and not scope_defined:
    trigger_warning("Unbounded owner scope: missing minimal proving scope")

# 4. 极值最高级无界拦截 (Superlatives Gate)
for sup in ["全球第一", "全网最年轻", "首个", "业界领先"]:
    if sup in text and not bounded_by_qualifiers:
        trigger_warning("Unbounded superlative without qualification")
```
